# 把「黑塔·整机」的设置搬进 DSH —— 已实施

> 状态：**已实施并在真机验证**（2026-09-26）。
> 底稿是工作区根目录的 `_herta-settings-統合設計.md`（那份写的是待确认的施工图，
> 本文记的是**实际落地的东西**，以及和施工图不一致的地方）。

## 1. 目标与结果

**目标**：整机的设置原本散在四处、各有各的存法，用户改一个偏好要开她的应用、
进她自己的设置面板。现在 DSH 设置里**单开一页「黑塔」**，改哪儿都写回她读的文件。

**结果**（都在 0.1.7-rc.2 lab 上实测）：

```
DSH 设置 ▸ 黑塔
  ├─ 界面       界面语言 / 对话语言 / 主题
  ├─ 窗口与更新  关闭时收进托盘 / 自动检查更新 / 3D 设备卡
  ├─ 语音       语音引擎 / 实时语音
  └─ 工作区     同步到工作区（路径，可从 DSH 已登记的工作区里选）
               做梦 / 推理档位 / 工具契约 / 黑塔的模型 / 板砖的模型
```

一页 14 项、分四组，不是一条自动生成的表单。

## 2. 数据流（一个真相来源）

```
DSH 设置页（settings.section ▸ 黑塔）
  │  ctx.configForms.get("herta").set(field, value)
  ▼
profile/cordis.patch.yml 的 herta 条目            ← 唯一真相
  │  loader 把新值提交进 volatile 引用（不重挂插件）
  ▼
宿主 loader/volatile-update
  │  src/host/settings-sync.js
  ├─► %APPDATA%\Herta\settings.json              只并写我们管的键
  └─► <workspace>\.herta\settings.json           同上；未指定工作区则跳过
```

整机（`Herta.exe`）**不知道 DSH 存在** —— 它照旧读自己那两份文件。

## 4. 三条不变量（都有单测钉住）

1. **只写用户真的在 DSH 里覆盖过的字段。**
   判据是 `settings.describe()` 里那条的 `user` 层有没有这个键 ——
   不是比较值（「显式设成默认值」与「从没设过」在值上一样、意图不同）。
   没被覆盖的字段在整机文件里**一个字节都不动**。
   没有这条，第一次挂载就会拿 schema 默认把她所有偏好抹平，
   而现象只是「设置被重置了」，没人看得出是谁干的。
   出口是每项的 `↺ 跟随整机`（见 §4.1）—— 那条声明记在 `followedFields` 里。
2. **只并写我们管的键。** 读-改-写，`windowState` / `minimaxVoice`
   等运行时事实原样保留（整机自己按 750ms debounce 写窗口几何，覆盖它等于制造 bug）。
3. **宁可不写，不可写错。** 整机读全局文件时**任一字段非法就整份回落 `{}`**
   （`app-global-settings.ts:131-175`），所以写回前一律过 `isManagedValue`。
   同理，`locale=""` / `interactionLanguage="follow"` 必须走**删键**而不是写空串。

另外：**首次挂载会把整机当前的值搬进来**（`readHeretaSeed`），
只搬「她那边真的写了、且值合法」的字段。实测第一条日志就是：

```
[dsh-herta] 从整机迁移设置：interactionLanguage, theme, deviceScene, voiceEngine, realtimeVoice
```

`locale` 没进这一行是**对的** —— 她那份文件里没有这个键，缺席 = 跟随系统。

### 4.1 「跟随整机」：那条单向门必须有一个出口

不变量 1 与种子合起来会产生一个**单向门**：种子会把整机那边有值的字段补进
`user` 层（这样页面显示的是真值），于是某项一旦被种过，用户就只能改它、
**不能退回「跟随她自己的文件」** —— 清掉覆盖会被下一轮种子立刻重新接管，
按钮看起来毫无作用。

所以页面上每一项在「被覆盖过」时会显示一个 **`↺ 跟随整机`**，
而它写的不是「删掉那个键」，而是一条**声明**：Config 里的
`followedFields: string[]`（volatile 数组字段，不占 UI）。宿主读它并跳过种子。

为什么这个记录位必须是 volatile：`@deepseek-ai/dsh-settings` 的 `write()`
用 `isVolatilePath` 逐个校验待写路径，**非 volatile 的字段根本写不进去**
（抛 `Config field "x" is not volatile`）。也就是说「另开一个非 volatile 的记录位」
在这套 API 下做不到。代价是它出现在命名空间 schema 里，无害。

实测（lab）：

- 挂载后 4 项被种子接管 → 页面出现 4 个 `↺ 跟随整机`。
- 点「主题」那一行的复位 → 剩 3 个；profile 补丁里 `theme` 消失、
  多出 `followedFields: [theme]`；**她的 `settings.json` 一字未动**。
- **重启后不再迁移 `theme`**（启动日志没有那一行）—— 声明真的持久。

## 6. 两个踩过的坑（都写进代码注释了）

### 6.1 `ctx.inject()` 开的是**另一条 fiber**

`loader/volatile-update` 只发给该条目**自己的 fiber**
（`cordis-plugin-loader/lib/index.js:417-420`：
`self[Context.filter] = (owner) => owner.fiber === fiber`），
而 `ctx.inject(deps, cb)` 在 cordis 里就是 `this.plugin({inject, apply: cb})`
（`cordis/lib/index.js:1600-1606`），`plugin()` 会 `new Fiber(...)`。

于是把监听器挂在 inject 的**子上下文**上会**静默收不到事件**：
设置页点一下、`cordis.patch.yml` 跟着变、整机的文件纹丝不动，一条报错都没有。
实测踩到过一次；现在监听器挂在 `apply` 的 ctx 上，用闭包里的 `settingsService` 干活。
（同一个原因，`settings.configure({auto:false}, owner)` 必须显式传 `ctx.fiber`
—— 这也是官方插件都这么写的理由。）

### 6.2 客户端 bundle 里不能用 `import()` 取种子模块

客户端 bundle 被包成 `__ModuleLoader__.load({factory: (require) => …})`，
**外壳冻结的模块表只通过工厂参数 `require` 暴露**。esbuild 会把**外部**模块的
动态 `import()` 原样保留，于是浏览器拿原生解析器去解析，报
`Failed to resolve module specifier '@deepseek-ai/dsh-client-ui-primitives'`。

静态 import 会正确变成 `require("…")`，但它在**求值期**执行：模块不在表里就让
整份 bundle 失败。所以 `src/client/index.tsx` 的 `loadSeedModule(id)` 用
**变量 specifier** 调一次运行时的 `require` —— 落到工厂参数上（正确通道），
又不被构建期解析，失败能被 `try` 关在这一页里。

## 7. 部署与验证

```powershell
# 构建 + 镜像进目标 profile（默认是 herta-lab，正式环境用 DSH_PROFILE_DIR）
$env:DSH_PROFILE_DIR="C:\Users\梦源\.dsh\profiles\desktop"
node scripts\deploy.mjs
# 然后**重启 dsh**（宿主半侧与客户端 bundle 都是启动时加载的）
```

单元测试（无需 DSH 运行时）：

```powershell
node scripts\test-herta-settings.mjs   # 74 项：字段表/校验/写回意图/合并/真落盘
node scripts\test-voice-settings.mjs   # 50 项：拼给她界面的 RealtimeVoiceState
```

真机验证做过的事（0.1.7-rc.2 lab，`dsh-017-lab`）：

- 首次挂载：日志打出「从整机迁移设置：…」，profile 补丁出现 `herta` 条目，
  **她的 `settings.json` 与运行前逐字节相同**（SHA-256 一致）——
  证明「没改的字段不写」这条不变量在真实文件上成立。
- 在 DSH 设置页点「深色」：`cordis.patch.yml` 变 `theme: dark`，
  她的 `settings.json` 也变 `dark`，而 `windowState` / `minimaxVoice` 一字未动。
- 设置导航里出现独立的「黑塔」一页（order 30，在「Agent 预设」之后）。
- 工作区那组能从 DSH 已登记的工作区里选（`settings.section` 的标准 prop `useWorkspaces`）。

**未做真机验证的一项**：工作区文件的写回（`<workspace>\.herta\settings.json`）——
它在单测里覆盖了「只并写自己的键 / 报告失败 / 工作区不存在就不写」，
真机路径与全局那份是同一个 `syncHertaSettings`，只是没在 lab 里制造副作用去点。
